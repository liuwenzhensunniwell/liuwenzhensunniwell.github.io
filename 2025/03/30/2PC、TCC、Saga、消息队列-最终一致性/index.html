2PC、TCC、Saga、消息队列+最终一致性

1. 2PC（两阶段提交）

原理

- 阶段 1 - 准备阶段（Prepare）: 协调者询问所有参与者是否可以提交事务，参与者执行本地事务并锁定资源，但不提交，返回“准备就绪”或“失败”。
- 阶段 2 - 提交阶段（Commit）: 如果所有参与者都返回“就绪”，协调者通知提交；若有任一参与者失败，则通知回滚。
  • 角色: 协调者（Coordinator）和参与者（Participants）。

优点

  • 强一致性: 保证所有参与者要么全提交，要么全回滚。
  • 简单: 实现逻辑清晰，适合小型分布式系统。

缺点

  • 性能瓶颈: 同步阻塞，参与者需等待协调者指令，延迟较高。
  • 单点故障: 协调者宕机可能导致事务挂起。
  • 资源锁定: 准备阶段资源被锁，影响并发性。

适用场景

  • 对一致性要求极高、并发较低的场景（如金融转账核心系统）。
  • 参与者数量少、事务短的系统。

实现示例

  • XA 协议（如 MySQL XA 事务）。

2. TCC（Try-Confirm-Cancel）

原理

  • 三阶段:
    • Try: 尝试执行业务，预留资源（不真正提交）。
    • Confirm: 确认执行业务，正式提交资源。
    • Cancel: 如果失败，取消操作，释放资源。
    • 补偿机制: 每个操作需定义对应的回滚逻辑。

流程

优点

  • 高性能: 异步执行，无长时间资源锁定。
  • 灵活性: 适合复杂的业务逻辑，可自定义补偿。

缺点

  • 开发成本高: 需为每个操作实现 Try、Confirm、Cancel 三套接口。
  • 一致性稍弱: 依赖补偿，可能短暂不一致。

适用场景

  • 高并发场景，如电商下单、秒杀系统。
  • 需要业务灵活性但允许短暂不一致的系统。

实现示例

3. Saga

原理

  • 分段事务: 将大事务拆分为多个子事务，每个子事务独立提交。
  • 补偿机制: 若某子事务失败，执行前序子事务的补偿操作（回滚）。
  • 两种模式:
    • 编排模式: 中心化协调者控制执行顺序。
    • 协作模式: 子事务通过事件互相触发。

流程

优点

  • 高吞吐量: 无全局锁，子事务独立提交。
  • 容错性强: 通过补偿恢复一致性。

缺点

  • 复杂性: 需设计每个子事务的补偿逻辑。
  • 一致性弱: 中间状态可能被外部看到。

适用场景

  • 长事务场景，如订单支付-发货-物流。
  • 对最终一致性可接受的业务。

实现示例（编排模式）

4. 消息队列 + 最终一致性

原理

  • 异步解耦: 主事务提交后，通过消息队列（如 RocketMQ、Kafka）通知其他服务执行本地事务。
  • 重试机制: 若下游服务失败，依赖消息队列重试或人工补偿。
  • 最终一致性: 不保证实时一致，但最终数据一致。

流程

优点

  • 高性能: 异步处理，降低主事务延迟。
  • 解耦: 服务间独立，易扩展。
  • 容错: 重试机制保障可靠性。

缺点

  • 一致性延迟: 数据可能短暂不一致。
  • 复杂性: 需处理消息丢失、重复消费等问题。

适用场景

  • 高并发、允许延迟一致的场景，如订单状态同步、日志记录。
  • 跨服务协作的业务。

实现示例（RocketMQ）

对比总结

方案 一致性 性能 复杂度 资源锁定 适用场景
2PC 强一致性 低 中 是 小型强一致性系统
TCC 最终一致性 高 否 否 高并发复杂业务
Saga 最终一致性 高 否 否 长事务流程
MQ+最终一致 最终一致性 很高 中 否 高吞吐量异步场景

选择建议

  • 2PC: 适合传统数据库事务，参与者少且一致性要求高。
  • TCC: 适合电商、秒杀等需要高并发和灵活补偿的场景。
  • Saga: 适合跨服务的长事务，如订单-支付-物流。
  • 消息队列: 适合高吞吐量、解耦的业务，常见于分布式系统。
